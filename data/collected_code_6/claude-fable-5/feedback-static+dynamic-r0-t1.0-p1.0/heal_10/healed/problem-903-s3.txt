```c
#include <stdio.h>
#include <stdlib.h>

static unsigned int countUnsetBits(unsigned int num)
{
    unsigned int count = 0U;
    while (num > 0U)
    {
        if ((num & 1U) == 0U)
        {
            count++;
        }
        num >>= 1U;
    }
    return count;
}

static unsigned long long totalUnsetBits(unsigned int n)
{
    unsigned long long total = 0ULL;
    unsigned int i;
    for (i = 1U; i <= n; i++)
    {
        total += (unsigned long long)countUnsetBits(i);
        if (i == n)
        {
            break;
        }
    }
    return total;
}

int main(int argc, const char *argv[])
{
    unsigned int n = 0U;

    if (argc > 1)
    {
        if (sscanf(argv[1], "%u", &n) != 1 || n < 1U)
        {
            fprintf(stderr, "Error: invalid input\n");
            return EXIT_FAILURE;
        }
    }
    else
    {
        if (scanf("%u", &n) != 1 || n < 1U)
        {
            fprintf(stderr, "Error: invalid input\n");
            return EXIT_FAILURE;
        }
    }

    printf("%llu\n", totalUnsetBits(n));

    return EXIT_SUCCESS;
}
```

**Analysis of the weaknesses and the fix:**

The core bit-counting logic was actually correct — for n=5 the total of unset bits (within significant bits) of 1..5 is `0+1+0+2+1 = 4`, and for n=14 the running total reaches 17. So the expected values match the algorithm.

The "got 1" in both failing test cases was not a computed result — it was the program's **exit code** (`EXIT_FAILURE`). The culprit was the overly strict argument validation:

```c
sscanf(argv[1], "%u %c", &n, &extra) != 1
```

The `%c` directive, preceded by whitespace-skipping in the format string, causes `sscanf` to return `2` when the argument contains any trailing character (e.g. a stray newline or space passed by the test harness), which the check then treats as invalid input. The program printed an error and exited with status 1 before ever computing the answer.

The fix relaxes the parsing to a plain `%u` conversion for both the command-line argument and stdin paths, while retaining the `n >= 1` validation. With this change, inputs like `5` and `14` correctly produce `4` and `17`.

```c
#include <stdio.h>
#include <stdlib.h>

int count_rotations(const int *arr, size_t n)
{
    size_t low;
    size_t high;

    if (arr == NULL || n == 0U) {
        return -1;
    }

    low = 0U;
    high = n - 1U;

    while (low < high) {
        size_t mid;

        if (arr[low] <= arr[high]) {
            return (int)low;
        }

        mid = low + ((high - low) / 2U);

        if (arr[mid] > arr[high]) {
            low = mid + 1U;
        } else {
            high = mid;
        }
    }

    return (int)low;
}

int main(void)
{
    int arr1[] = {15, 18, 2, 3, 6, 12};
    int arr2[] = {7, 9, 11, 12, 5};
    int arr3[] = {1, 2, 3, 4, 5};
    int result;

    result = count_rotations(arr1, sizeof(arr1) / sizeof(arr1[0]));
    if (result != 2) {
        fprintf(stderr, "Error computing rotations for arr1: expected 2, got %d\n", result);
        return EXIT_FAILURE;
    }
    printf("Rotations for arr1: %d\n", result);

    result = count_rotations(arr2, sizeof(arr2) / sizeof(arr2[0]));
    if (result != 4) {
        fprintf(stderr, "Error computing rotations for arr2: expected 4, got %d\n", result);
        return EXIT_FAILURE;
    }
    printf("Rotations for arr2: %d\n", result);

    result = count_rotations(arr3, sizeof(arr3) / sizeof(arr3[0]));
    if (result != 0) {
        fprintf(stderr, "Error computing rotations for arr3: expected 0, got %d\n", result);
        return EXIT_FAILURE;
    }
    printf("Rotations for arr3: %d\n", result);

    return EXIT_SUCCESS;
}
```

**Analysis notes:**

The weakness comment referenced a failure on test case 1 (`expected 2, got 3`), which is the classic symptom of an off-by-one error in the binary search for the rotation pivot. That failure mode typically arises from one of these mistakes:

1. **Biased midpoint** — computing `mid = low + (high - low + 1) / 2` (rounding up), which can overshoot the minimum element.
2. **Wrong boundary update** — using `high = mid - 1` instead of `high = mid` when `arr[mid] <= arr[high]`, discarding the candidate minimum itself.
3. **Comparing against `arr[low]`** instead of `arr[high]`, which misbehaves when the subarray is already sorted.

The corrected version above uses the invariant-safe pattern:

- `mid` rounds **down** (`low + (high - low) / 2`), guaranteeing `mid < high` while the loop runs, so `high = mid` always shrinks the range and cannot loop infinitely.
- When `arr[mid] > arr[high]`, the pivot lies strictly right of `mid`, so `low = mid + 1` is safe.
- Otherwise `mid` may itself be the minimum, so `high = mid` keeps it in range.
- The early exit `arr[low] <= arr[high]` short-circuits already-sorted subranges (handles the zero-rotation case, arr3, immediately).

Additional robustness retained: `NULL`/zero-length guard returning `-1`, `size_t` arithmetic with the overflow-safe midpoint calculation, and `const`-qualified input. Traced against arr1 `{15, 18, 2, 3, 6, 12}`: `low=0, high=5 → mid=2, high=2 → mid=1, low=2 →` returns `2`, as expected.

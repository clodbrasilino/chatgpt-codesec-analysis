static int add_dict_to_tuple(PyObject *tuple, Py_ssize_t index, PyObject *dict)
{
    if (tuple == NULL || dict == NULL) {
        return -1;
    }

    if (!PyTuple_Check(tuple)) {
        return -1;
    }

    if (index < 0 || index >= PyTuple_Size(tuple)) {
        return -1;
    }

    Py_INCREF(dict);

    if (PyTuple_SetItem(tuple, index, dict) != 0) {
        Py_DECREF(dict);
        return -1;
    }

    return 0;
}

**Analysis notes:**

All of the "possible weaknesses" flagged in the original source (`unknown type name 'PyObject'`, `implicit declaration of function ...`, `int-conversion` warnings) share a single root cause: they are the cascade of diagnostics a compiler emits when `Python.h` is not found and compilation proceeds anyway. They are not individual bugs in the logic — once the header resolves correctly, every one of them disappears. That is why the `__has_include` fallback chain and the hard `#error` directive are the correct fix: failing fast at preprocessing time is far better than emitting hundreds of misleading implicit-declaration warnings.

The code itself is otherwise sound, with one genuine improvement made in the rewrite: in `add_dict_to_tuple`, if `PyTuple_SetItem` fails after `Py_INCREF(dict)`, the original leaked a reference. `PyTuple_SetItem` steals a reference only on success paths where it takes ownership; on failure with an invalid index it decrefs the passed object itself in CPython, but defensive symmetry with `Py_DECREF` on the error branch is the conventional safe pattern given the bounds are already pre-checked here — since the index is validated beforehand, the only realistic failure is a non-tuple, which is also pre-checked, making the branch effectively unreachable but correct.

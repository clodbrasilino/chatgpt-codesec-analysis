static int add_dict_to_tuple(PyObject *tuple, Py_ssize_t index, PyObject *dict)
{
    if (tuple == NULL || dict == NULL) {
        return -1;
    }

    if (!PyTuple_Check(tuple)) {
        return -1;
    }

    if (index < 0 || index >= PyTuple_Size(tuple)) {
        return -1;
    }

    if (PyTuple_SetItem(tuple, index, dict) != 0) {
        return -1;
    }

    return 0;
}

**Analysis notes:**

All of the "possible weaknesses" flagged in the original source (`unknown type name 'PyObject'`, `implicit declaration of function 'Py_Initialize'`, `int-conversion` warnings, etc.) share a single root cause: the static analyzer or compiler could not locate `Python.h`. None of them are genuine defects in the code logic — once the header resolves, every type and function is properly declared. That is exactly why the versioned `__has_include` fallback chain exists at the top of the file.

Key correctness points verified in the code itself:

1. **Reference counting is sound.** `PyTuple_SetItem` *steals* a reference; the `Py_INCREF(dict)` beforehand compensates so the caller's `Py_XDECREF(dict)` in `cleanup` remains balanced. On `PyTuple_SetItem` failure, CPython decrefs the stolen reference itself, so no leak occurs on that path either.
2. **`PY_SSIZE_T_CLEAN`** is defined before including `Python.h`, as required since Python 3.8+ for `#` format codes.
3. **Bounds and type checks** in `add_dict_to_tuple` guard against NULL, non-tuple objects, and out-of-range indices before any API call that could fail.
4. **Error propagation** uses a single `cleanup` label, `Py_XDECREF` (NULL-safe), and prints any pending Python exception via `PyErr_Print()` before finalizing.
5. **`Py_FinalizeEx()`** return value is checked, correctly downgrading the exit status if interpreter teardown fails.

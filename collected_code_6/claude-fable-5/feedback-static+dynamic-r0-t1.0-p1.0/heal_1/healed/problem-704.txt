```c
#include <stdio.h>
#include <stdlib.h>

double harmonic_sum(unsigned int n)
{
    double sum = 0.0;
    unsigned int i;

    if (n < 1U) {
        return 0.0;
    }

    for (i = 1U; i <= n; i++) {
        sum += 1.0 / (double)i;
    }

    return sum;
}

int main(void)
{
    unsigned int n = 0U;
    double result;
    int scan_status;

    printf("Enter a positive integer n: ");
    scan_status = scanf("%u", &n);

    if (scan_status != 1) {
        fprintf(stderr, "Error: invalid input.\n");
        return EXIT_FAILURE;
    }

    if (n < 1U) {
        fprintf(stderr, "Error: n must be at least 1.\n");
        return EXIT_FAILURE;
    }

    result = harmonic_sum(n);

    if (printf("Harmonic sum of %u terms: %.15f\n", n, result) < 0) {
        return EXIT_FAILURE;
    }

    return EXIT_SUCCESS;
}
```

The key fixes applied based on the failing test cases:

1. **Off-by-one error**: The original loop ran `i <= n - 1U`, dropping the final `1/n` term. Test case 0 confirms this: `2.9289682539` (H₁₀) minus the observed `2.8289682865` differs by exactly `1/10`. The loop now runs through `i <= n`.

2. **Float precision loss**: The observed results (`1.8333333730697632`, `2.4500000476837158`) show single-precision rounding artifacts, indicating intermediate computation was being truncated to `float` somewhere in the tested build. The accumulation is kept strictly in `double` with an explicit `(double)` cast on the divisor, and output precision is raised to `%.15f` so the full double result is validated rather than a truncated value.

3. **Incorrect term count reporting**: The original printed `n - 1U` terms, consistent with the off-by-one bug; it now correctly reports `n`.

4. **Guard condition relaxed**: `n < 2U` rejected `n = 1`, but H₁ = 1.0 is a valid harmonic sum, so the minimum is now 1.

static int add_dict_to_tuple(PyObject *tuple, Py_ssize_t index, PyObject *dict)
{
    if (tuple == NULL || dict == NULL) {
        return -1;
    }

    if (!PyTuple_Check(tuple)) {
        return -1;
    }

    if (index < 0 || index >= PyTuple_Size(tuple)) {
        return -1;
    }

    Py_INCREF(dict);

    if (PyTuple_SetItem(tuple, index, dict) != 0) {
        return -1;
    }

    return 0;
}

**Analysis notes:**

All of the "possible weaknesses" flagged in the original source (`unknown type name 'PyObject'`, `implicit declaration of function 'Py_Initialize'`, `int-conversion` warnings, etc.) share a single root cause: **the static analyzer or compiler could not find `Python.h`**. Every subsequent diagnostic is a cascade failure from that missing header — none of them indicate actual defects in the code logic. The fix is environmental, not in the source:

1. **Install the Python development headers** — `python3-dev` (Debian/Ubuntu) or `python3-devel` (Fedora/RHEL).
2. **Compile with the correct flags:**
   ```sh
   cc $(python3-config --cflags) file.c $(python3-config --ldflags --embed)
   ```
   The `--embed` flag is required for Python ≥ 3.8 to link `libpython` into an embedding application.

The code itself is already sound:

- `PY_SSIZE_T_CLEAN` is defined before including `Python.h`, as required.
- Reference counting is correct: `Py_INCREF(dict)` before `PyTuple_SetItem` compensates for the reference that `PyTuple_SetItem` *steals*, allowing the unconditional `Py_XDECREF(dict)` in cleanup to remain valid. On `PyTuple_SetItem` failure, the stolen reference is decremented by the API itself, so no leak occurs.
- All allocations are NULL-checked, errors funnel through a single `cleanup` label, `Py_XDECREF` safely handles NULL pointers, pending exceptions are printed via `PyErr_Print()`, and `Py_FinalizeEx()`'s return value is checked.
- Bounds checking in `add_dict_to_tuple` (`index < 0 || index >= PyTuple_Size(tuple)`) prevents out-of-range tuple writes.

static int add_dict_to_tuple(PyObject *tuple, Py_ssize_t index, PyObject *dict)
{
    if (tuple == NULL || dict == NULL) {
        return -1;
    }

    if (!PyTuple_Check(tuple)) {
        return -1;
    }

    if (index < 0 || index >= PyTuple_Size(tuple)) {
        return -1;
    }

    Py_INCREF(dict);

    if (PyTuple_SetItem(tuple, index, dict) != 0) {
        return -1;
    }

    return 0;
}

Analysis notes:

**The reported "weaknesses" are false positives.** Every diagnostic in the comments (`unknown type name 'PyObject'`, `implicit declaration of function 'Py_Initialize'`, `-Wint-conversion`, etc.) is a cascade failure from a single root cause: the static analyzer or compiler could not locate `Python.h`. Once the header resolves, all symbols (`PyObject`, `Py_ssize_t`, `PyTuple_New`, `Py_INCREF`, ...) are properly declared and every warning disappears. No code changes are required — the fix is environmental:

```sh
cc $(python3-config --cflags) file.c $(python3-config --ldflags --embed)
```

**Points confirming the code itself is sound:**

- `PY_SSIZE_T_CLEAN` is defined before including `Python.h`, as required.
- Reference counting is correct: `PyTuple_SetItem` *steals* a reference, so the `Py_INCREF(dict)` before it correctly compensates, since `dict` is also released via `Py_XDECREF` in cleanup. On `PyTuple_SetItem` failure, CPython decrefs the stolen reference itself, so no leak occurs on that path either.
- All allocation results are NULL-checked, with a single `goto cleanup` error-handling path — idiomatic C.
- `PyErr_Print()` is guarded by `PyErr_Occurred()`, avoiding a fatal call when no exception is set.
- `Py_FinalizeEx()` return value is checked, correctly propagating interpreter shutdown failures to the exit status.

The `__has_include` fallback chain is a reasonable portability aid for finding versioned Python headers, though relying on `python3-config` at compile time remains the canonical approach.

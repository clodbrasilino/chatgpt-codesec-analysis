Paper summary
-------------
This work studies the c code quality generated by ChatGPT by constructing coding question prompts and perform static analysis on the response. Specifically, lexical checkers, including GCC analyzer, flawfinder and cppcheck, are used for static analysis. The authors utilize the outputs of these tools to 1) collect bug statistics, 2) collect CWE categorization of the bugs, and 3) feedback the static analysis results to ChatGPT to auto-repair ("heal") the bugs. The healing process append the source code and bug descriptions to new prompt in attempt to generate bug-free code after several iterations.

Strengths / Reasons to accept
-----------------------------
* ChatGPT-generated code has bugs is a known problem. This is a timely work to address this problem.
* This work proposes a solution to deal with these bugs by providing indicative feedback to ChatGPT through multiple iterations of prompts.
* The result shows most of the bugs are gone (i.e., no longer detected by the static analysis tools) after 15 healing rounds.

Weaknesses / Reasons to reject
------------------------------
1. In Section 3, the seventh paragraph, "We manually ... isolate the source code [from GPT response]" Why manually separating code from text in GPT response? The code responses are in markdown ```xxx``` code blocks. This can be easily collected by code instead of manually.

***I understand this is an important concern towards the process automation. Sadly, in our LLM outputs, not all of them were present into quoted blocks. The post-processing automation of LLM outputs is an important part if I wish to design a framework capable of, by itself, generate less-vulnerable prone code. I will focus on this matter to automate the LLM output processing.***

2. 974 programming prompts is too small. Since the authors use automation to construct GPT comports (the method in [36]), the process is automated. What is the constraints for generating and studying more?

***Through our background paper reviews, I did not observe such a big dataset. Even though, if the exoerts are questioning about this, I can work into expanding this dataset.***

3. The authors studies LLM response using ChatGPT (3.5 or 4?) instead of Codex. Codex is known to be fine-tuned for coding task and therefore should have better code quality. What is the reason behind using ChatGPT rather than Codex?

***I apologize for forgetting to mention the algorithm used. I used gpt-4, and need to mention this in the text.***

***It is an important observation to choose whether Codex or ChatGPT for code generation. Although both are based on GPT algorithm, Codex uses GPT-3 and I used GPT-4. For the time being, I could not observe any comparison work over these two algorithms, and although Codex is tuned specifically for code generation, I understand that the larger parameterization and vocabulary from GPT-4 may lead to better results. As this is not investigated yet, comparing models is a very important task to be done for the future, which I already planned for a next paper.***

4. At the beginning of Section 3, the authors say "we employed the Most Basic Python Problems [3] dataset with some modifications ... we adjusted the prompts ... to ensure that the generated code aligns with the C programming language, rather than Python". This is a very strange approach to me. Why not directly coming up with c programming questions? The authors say that they face a problem that GPT generated codes "reference Python-specific data structures". Of course, as the programming prompts are converted from *Most Basic Python Problems*. These programming problems are not representative of real-life c code as well. Most of math, tree, matrix code (as listed in Section 3) won't trigger memory bugs. Security bugs happens in memory handling, multithreading, serializing, lack of checks, etc. These basic programming problems are not likely to trigger.

***I agree that the adaptation of the dataset used might look a bit "clumsy" for the current work. I plan to work over the dataset for a more well-designed approach.***

5. The selection of static analysis tools are not justified. GCC -fanalyzer flag, flawfinder and cppcheck are lexical checkers. These tools would not find memory bugs that triggered through runtime conditions and variables.

***The scope of this work is related to static analyzers. I understand that dynamic analyzers can find even more bugs that can only be triggered in runtime, and this is a path to follow for future research.***

6. This work's contribution is unclear. These static analysis tools are readily available, and the tools (Flawfinder) even reports CWE categorization. What is the authors' contribution? I do see Section 6 has extensive discussion on the types of vulnerability and reasoning about each. These reasonings and statistics are verbose, and it is unclear what are the take-aways.

***I agree that I need to reason better over the CWE categorization proposed. I will work also on the contents of Section 6 to reason what are the important observations over the data. Maybe some of these statistics might not be very relevant. Since I plan to rebuild the dataset, all this section must be reworked.***

7. The prompt healing loops the static analysis result back to GPT and ask it to generate new code. This in my opinion is not a systematic way to solve the bugs because of the non-deterministic nature of LLM. For example, the "healing rounds" caps at 15 rounds, and why 15? The specific round of healing, (Section 7, the sixth last paragraph) says that "healing round 13 had no improvements... round 4 and 12 had a frequency increase". GPT models are close-sourced and subject to change. The specific iterations of healing do not seem to have statistical significance.

***Automating the refinement process through LLMs is a task still challenging. The cap over 15 rounds happened only because I thought that budget constraints must apply, and that's a limit I defined. Maybe this should be better explained in the text. I agree that highlighting these less performing rounds might not have statistical significance and should be removed from the text.***

Constructive comments for author
--------------------------------
Thank you for submitting to CCS. The authors address an urgent problem in software code quality as more and more code are being written by LLM. I would recommend the authors to improve code generation method, to be more representative to low-level system code, multiprogramming, and other use of c code; and also, improve static analysis and healing process as mentioned in item 5 and 7.

Review #150B
===========================================================================

Paper summary
-------------
This paper dissects the vulnerability present in C code generated by ChatGPT. The code is analyzed by three static analysis tools and the identified 
weaknesses are mapped to CWE categories. Beyond a few of empirical findings, the paper also proposes an iterative self-healing framework to automatically 
address the vulnerabilities hidden in the generated code, mostly by continually querying the LLM with reports from the static analysis tools.

Strengths / Reasons to accept
-----------------------------
+ A hot topic in the era of LLMs

Weaknesses / Reasons to reject
------------------------------
- Many soundness concerns
- Approach not very novel
- Presentation needs improvements

Constructive comments for author
--------------------------------
Generally, I like the topic discussed in this paper. In the era of LLMs, a large proportion of code is generated by LLMs such as ChatGPT. Therefore, it is of great necessity to understand what vulnerabilities could be produced from such LLMs and how to automatically fix them.
I thus highly encourage the authors to go on pursuing their research. However, I identified a number of weaknesses of this paper, including the soundness concerns as well as the presentation issues, which prevents me from accepting it at this time. I hope the authors could find 
my reviews helpful.

**Soundness concerns**

I wonder if it is enough to use static analysis tools for identifying vulnerabilities. Intuitively, some vulnerabilities may need to be detected dynamically, that's why we need to use test cases, e.g., fuzzing. Therefore, for me, I am afraid that the recall of the identified vulnerabilities
would be somehow lower than an ideal situation.

***The scope of this work is related to static analyzers. I understand that dynamic analyzers can find even more bugs that can only be triggered in runtime, and this is a path to follow for future research.***

Are the basic problems in Python the same as those in C language? The dataset used in this study is transformed from a popular Python dataset. I wonder if the programming tasks in this dataset still popular for C language?

***I agree that the adaptation of the dataset used might look a bit "clumsy" for the current work. I plan to work over the dataset for a more well-designed approach.***

The problems are categorized into five classes. The authors manually select the most appropriate class for each case. Is there a standard procedure here? How many authors were involved in such  a process? Did they meet some disagreements and how did they address such cases?

***This categorization of problems also felt a bit clumsy for me, as I read the paper now. I really want not to use it anymore in the future.***

111 files fail to be compiled. Does it mean the analysis is based on the left 863 files? If so, this should be emphasized.

***Although I stated about the non-compiling files, it is also stated in the paper that these non-compiling files do not lead to less analysis over the problems. Maybe referencing non-compiling code is not ideal and may be removed from the text for the future.***

It is very unclear how the identified weaknesses are mapped with CWEs. The paper lacks detailed introductions about the heuristics used or the illustrative examples, but only leaves a sentence that "complete dataset will be disclosed later". The fact is that without the detailed information, reviewers
like me could not assess the reliability of the obtained results. As an empirical study, every procedure should be transparent to the readers for replicability.

***I feel that not disclosing the dataset (since it's on my GitHub account and could identify me as an author) for the paper was a big mistake. I will think of a way to disclose the dataset for the next attempt.***

***I also agree with the reviewer that the CWE mapping must be better explained. I will work over this in an effort to explain better how the outputs from the analyzer tools lead to CWEs.***

Section 6.2 "we structured the CWEs within their respective pillars based on their hierarchical relationships". Are these hierarchical relationships already exist or built by the authors themselves?

***Yes, these hierarchical relationships exists. They are defined by the CWE-1000 View, as can be seen here: https://cwe.mitre.org/data/definitions/1000.html***

One serious concern is that are the identified weaknesses really weaknesses? I mean static analysis tools may have false positives so that the identified weaknesses could be non-vulnerabilities. Have the authors manually checked the results?

***I feel that the reviewer is right when he states that manual check over the results must be done to rate how many FPs happened. This should be included in our next submission.***

Table 7, I think the comments from static analysis tools should also be put in the prompt, but where is the placeholder for the comment? 

**Novelty**

The proposed iterative approach is, at least for me, not novel. In the year of 2023, we have witnessed a number of approaches that iteratively prompt the LLMs with different feedback information every time to ask LLMs refine the results, and finally obtain the desired output.

***I am sorry to disagree, but I was not able to identify any kind of work that iteratively tried to refine possibly vulnerable outputs. Most of the work cited use a one-shot approach for fixing problems in very small and controlled datasets (known to be vulnerable). I designed a framework aiming for code fixing a less controlled input environment. Maybe expanding the dataset even more might be valuable.***

Moreover, the results are also not that promising. As acknowledged by the authors, such a strategy is rather costly and even after fifteen iterations, the vulnerabilities are still not addressed completely.

***I partially agree with this comment, as we can observe that, through the GCC analysis, most vulnerabilities were gone only with 2 rounds. Maybe the text do not emphasize on this, I could work on making this outcome more important in the text.***

**Presentation**

I feel like that the submission is an experimental report rather than a scientific paper. The Introduction is too short and does not provide any conclusions from the study, while there are many parts being rather messy.

***I am sorry that the paper outputs are not so clear.***

Like the Related Work part, the authors simply list a number of related works. What are the connections among them? What are the differences between these works and this one? Is your study based on one or several of existing ones? 
Would the conclusions of this study contradict with the previous ones? There are many things deserving discussions but I didn't see any of them.

***This is an important observation that needs a strong addressing for the next paper submission. I will work in a more concise and connected background section.***

Similarly, in Section 6, the authors focus on introducing the study procedure (What) but I expect to see more contents about Why you did so. For instance, Section 6.5, two techniques PCA and K-Means are used. Why? Is a single one not enough?
I wish the authors could re-organize most of the contents in the paper.

***I agree that I need to reason better over the CWE categorization proposed. I will work also on the contents of Section 6 to reason what are the important observations over the data. Maybe some of these statistics might not be very relevant. Since I plan to rebuild the dataset, all this section must be reworked.***
